# ADR-0006: Vocus Reader Chrome Stripping Strategy

## Status
Accepted

## Date
2026-06-30

## Context
Imported Vocus articles opened in Monori's reader still showed distracting platform chrome:
- "方格子 vocus" header with "開啟 App" button
- Author metadata bar (avatar, badge, publish date)
- Ad interstitials ("即將進入廣告，捲動後可繼續閱讀") with reserved-height containers
- Bottom action toolbar (TOC, Share, Comment, Bookmark, Like)
- A fixed "×" close button at bottom-right

CSS-only hiding (`nav, header, footer { display: none }`) was insufficient because Vocus renders most chrome as `<div>` elements via React/Next.js, not semantic HTML tags.

## Decision
Use a three-phase JavaScript cleanup injected after the CSS ruleset, plus CSS `min-height: 0` to collapse ad container reserved space.

### Phase 1 — Content-path isolation
Walk up from `.editor-content-block` to `<body>`, hiding all sibling elements at each ancestor level (preserving `<style>`, `<script>`, `<link>` tags). This removes all non-content chrome regardless of tag name or class.

### Phase 2 — Fixed/sticky overlay removal
Iterate all `body *` elements and hide any with `position: fixed` or `position: sticky`. This catches floating toolbars, close buttons, and notification banners that may be deeply nested.

### Phase 3 — In-content ad removal
Find elements containing "廣告" text (< 200 chars) and walk up to their nearest ancestor that is a direct child of `.editor-content-block`, hiding that entire subtree. Also collapse iframe containers within the content block. A CSS rule (`min-height: 0 !important` on all content-block descendants) collapses reserved ad-slot heights that `display: none` alone cannot eliminate.

The cleanup runs immediately and again at 1 s and 3 s delays to handle dynamically loaded elements.

## Alternatives Considered

### CSS-only with specific class selectors
- Rejected: Vocus class names are generated by their build toolchain and change across deploys. Text-based or structural JS detection is more stable.

### `display: none` without `min-height` reset
- Tried: hid ad text but left a full-screen-height gap where the ad container reserved space via `min-height`.

### Shallow DOM scan (4 levels) for fixed/sticky elements
- Tried: missed the "×" close button which was nested deeper than 4 levels. Full `body *` scan (~20 ms) is acceptable for a one-time post-load cleanup.

## Consequences
- Vocus articles in reader mode show only article text — no ads, no toolbars, no header chrome
- The `min-height: 0` rule is aggressive but safe: article text elements don't use `min-height`
- If Vocus restructures their DOM so `.editor-content-block` no longer wraps the article, the cleanup will degrade gracefully (CSS still hides semantic elements; JS phases 2–3 still run)
- The 3-second delayed re-run covers lazy-loaded ads but won't catch ads injected much later; this is acceptable for the reading use case
